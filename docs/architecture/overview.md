# Architecture overview

The deterministic vertical slice has four layers. `packages/domain` defines canonical executable metrics, the wider available/planned registry, governed demo tenant profiles, bounded analysis, and versioned dashboard contracts. `packages/data` contains the canonical-measure engine and mock/SQLite repository adapters. `packages/application` owns the market-neutral template catalog, deterministic mock planner, provider-backed structured planner, per-series DashboardExecutor, and saved-dashboard service. The React manual builder edits the same validated v2 spec through bounded commands and session history. `apps/api` resolves the tenant, validates/instantiates specs, orchestrates execution, and exposes authorized saved-dashboard operations. `apps/web` renders returned v2 specs and results in English or Modern Standard Arabic.

Dependency direction is `web → API → application → domain/repository port`; the SQLite implementation remains behind that port. The browser never constructs source queries or sets country/currency. Builder filter values come from a tenant-scoped repository endpoint. The API allows only `demo-iq` and `demo-eg` in the prototype. This is a demo gate, not production authentication.

DashboardSpec v2 widgets contain stable-ID series. Each series maps to a canonical AnalyticsQuery under the same tenant, filters, and date range. The executor retains per-series success/error and aligns grouped rows by canonical key; missing values remain null. In a multi-series widget, only the first series may use top/bottom N and it determines the displayed keys. A failed selection makes the widget an error; successful later series cannot establish the requested selection. Aligned series retain value, rank, comparison, and change metadata. Line and bar charts accept only compatible types/units, while tables format each metric independently. The v1 JSON Schema is retained for historical clarity and is not accepted by new routes.

The common metric registry distinguishes `available` (24 deterministic formulas) from `planned` concepts such as DSO, customer churn, and supplier lead time. Planned metrics are discoverable through the API but fail executable-spec validation. The mock planner recognizes a bounded set of sales requests and edits in English, Modern Standard Arabic, Iraqi Arabic, and Egyptian Arabic. Provider-neutral planning evaluation cases cover mixed language and digit styles. The OpenAI-compatible HTTP adapter connects to a configured model endpoint; the mock planner remains the default. Canonical validation, semantic checks, and authorization apply to both paths.

Additive measures sum by default. Ratios and durations divide aggregated components; sales growth derives from a revenue comparison; snapshots use latest observation per entity. Calendar comparisons use UTC bucket arithmetic; template date presets use the tenant's configured local date. `dataThrough` records metric-specific tenant event coverage; optional `sourceAsOf` records known source synchronization time. The local adapters do not infer freshness from event dates. Monetary synthetic facts are assumed to be in each tenant's reporting currency, with no FX conversion or cross-currency aggregation.

DashboardSpec v2 optionally carries portable 12-column widget positions. Missing positions are derived deterministically for existing templates. The web grid adapter handles drag and resize; layout-only edits do not query analytics. Semantic builder edits re-execute through the existing API. Empty and incomplete builder drafts remain separate from executable specs. Browser-session undo/redo is bounded. A DashboardRecord has identity, ownership, scope, audit timestamps, and optimistic version independent of DashboardSpec.id. The SQLite dashboard repository is independent of the analytics source adapter. Manual and AI edits change only a working copy until Save; saved records reopen by URL. The browser persists only UI locale and last tenant preference, and the server revalidates membership and permissions.

The web workspace now presents an explicit creation launcher (AI, blank, or template), then contextual view, manual edit, and AI edit states. Templates stay immutable until Use template creates a working draft. Saved dashboards open in view mode; Save appears for unsaved or modified work, and AI edits remain local until Save. The sidebar keeps saved records separate from system templates. The selected synthetic demo identity is restored from browser session storage and revalidated by the server. A saved route is resolved only across that user's server-returned tenant memberships; the matching tenant becomes active before tenant-scoped metadata and analytics load.

## Web presentation

The web layer owns controlled System/Light/Dark preferences, semantic CSS tokens and centralized chart styling. Theme changes are local presentation updates, independent of UI language, working-draft dirtiness, analytics execution and record persistence. Responsive navigation keeps the library available through expanded/collapsed desktop navigation and a mobile modal drawer; detailed templates belong to creation. See [ADR 022](adr/022-web-presentation-themes.md) for ownership, accessibility and the future controlled tenant-branding boundary.
