# Data flow

`tenant header → controlled TenantProfile → market-neutral template, manual builder, or mock planner → DashboardSpec v2 validation → DashboardExecutor → tenant-scoped AnalyticsQuery per series → repository adapter → deterministic engine → AnalyticsResult per series → aligned widget rows → localized React renderer`.

The template path does not call the planner. The planner path produces the same v2 contract and passes the same validation. An edit produces DashboardPatch v2; the patch is applied atomically and the resulting dashboard is re-executed. Unknown planned metrics, SQL, incompatible chart units, and invalid analysis combinations are rejected before repository execution.

SQLite selects canonical source measures using tenant-bound parameters. Derived metrics are calculated from aggregated components; balances choose each entity's latest observation as of the period end. Grouped multi-series rows align on stable canonical dimension keys; no missing value is replaced by zero. Only the first series may use top/bottom N; its selected keys determine the displayed rows. If that selection fails, the widget reports an error even if other series succeeded. Each aligned series retains rank and comparison/change fields. Time keys remain chronological in either UI direction. `dataThrough` is the latest event date among the tenant's facts needed for a metric, independent of the selected query period. `sourceAsOf` is an adapter-supplied source synchronization/extraction timestamp and is absent for the local fixture unless explicitly configured. Neither adapter infers synchronization freshness from event dates.

`demo-iq` and `demo-eg` have distinct synthetic branches and customer records. The Iraq fixture has 420 customers and 155,232 canonical facts; Egypt has 360 customers and 146,304 facts. Both span October 2024 through September 2026 and share the same formulas, templates, and source-independent IDs. The fixture encodes growth, decline, seasonality, customer concentration, overdue balances, inventory pressure, and equipment/technician patterns. No source transaction currency or FX data is modeled.

Manual builder flow: `template/planner output or empty BuilderDraft → in-memory widget/filter/layout edit → validated DashboardSpec v2 or DashboardPatch v2 → existing execute endpoint → shared renderer`. Empty drafts and incomplete widget forms never reach the executor. Drag/resize commits only portable grid items after the gesture ends and does not execute analytics; semantic edits do. Branch and other filter choices come from tenant-scoped dimension discovery. Tenant switching reloads the active template and clears session history.

Saved dashboard flow: `authorized request context → SavedDashboardService → DashboardRepository → SQLite dashboard records`. A record ID is independent of the portable DashboardSpec.id. Create validates the spec and requires `dashboard:create`; read/list require `dashboard:view` and record visibility; update requires `dashboard:edit`, ownership and an expected version. A stale version returns 409. Private records are not disclosed to other users by ID. Dashboard persistence uses `DASHBOARD_DB_PATH`, independent of `ANALYTICS_PROVIDER`.

The web holds a working document as a template, unsaved draft, or saved record plus working spec. Manual and AI edits change the working spec and may execute analytics for preview; they do not write a record. Save creates or updates using the expected version; Save As creates a new record; Discard restores the last saved spec or abandons an unsaved draft. The browser route `/dashboards/:recordId` reloads a saved record. Local storage holds UI language and last tenant only. Startup revalidates the tenant against server membership. A language switch changes presentation only and leaves DashboardSpec intact.
